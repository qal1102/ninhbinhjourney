# Đường hoàn tác cho `202608290050_customer_multi_slot_booking.sql`

Tài liệu này tồn tại vì production **không có PITR và không có bản sao lưu vật lý**. Migration đổi khóa chính của một bảng đang chạy thật, nên phải có đường quay lại được viết sẵn — viết lúc đang bình tĩnh, không phải lúc đang hỏng.

## Bản sao lưu không phải là thứ cần ở đây

Ba lý do, theo thứ tự quan trọng:

1. **Migration chạy trọn trong một giao dịch.** Hỏng bất kỳ bước nào thì PostgreSQL tự cuộn lại toàn bộ. Không có trạng thái dở dang để mà phục hồi.
2. **Nới khóa chính không sửa và không xóa hàng nào.** Nó chỉ đổi quy tắc "thế nào là trùng". Mọi hàng cũ vẫn duy nhất theo bộ khóa rộng hơn.
3. **Đã thử trên chính cơ sở dữ liệu production** bằng một giao dịch kết thúc bằng `rollback`, ngày 29/08/2026: 6 hàng giữ nguyên, khóa chính mới đúng bốn cột, mỗi hàm đúng một bản.

Rủi ro thật không phải mất dữ liệu, mà là **áp xong rồi muốn quay lại mà không có đường**. Đó là thứ tài liệu này giải quyết.

## Điều kiện bắt buộc trước khi hoàn tác

Khóa chính cũ chỉ dựng lại được khi **mỗi cặp (tenant, product, site) còn đúng một hàng**. Nếu đã có ai thêm khung giờ thứ hai cho cùng một cơ sở, hoàn tác sẽ **xóa mất lịch bán thật**. Kiểm trước, đừng đoán:

```sql
select tenant_id, product_id, site_id, count(*)
from public.customer_product_capacity_templates
group by 1, 2, 3
having count(*) > 1;
```

Trả về hàng nào thì **dừng lại**. Lúc đó việc phải làm là quyết định giữ khung nào và bỏ khung nào — một quyết định kinh doanh của chủ dự án, không phải một câu lệnh.

## SQL hoàn tác

Chạy trọn trong một giao dịch. Đưa lược đồ về đúng trạng thái trước `202608290050`.

```sql
begin;

-- 1. Trả hàm giữ chỗ về chữ ký 7 tham số.
--    Thân hàm lấy nguyên văn từ `202608260049_erp_capacity_multi_bottleneck.sql`
--    dòng 373–645. Chép lại từ đó, đừng viết lại từ đầu.
drop function if exists public.customer_create_booking_hold(
  uuid, uuid, uuid, uuid, date, integer, timestamptz, timestamptz
);
-- <dán nguyên văn hàm 7 tham số từ 202608260049 vào đây>

-- 2. Trả dấu vân tay về 3 tham số.
drop function if exists public.customer_booking_payload_digest(
  uuid, date, integer, timestamptz
);
create or replace function public.customer_booking_payload_digest(
  p_product_id uuid,
  p_visit_date date,
  p_party_size integer
)
returns text
language sql
immutable
security invoker
set search_path = ''
as $$
  select encode(
    extensions.digest(
      p_product_id::text || ':' || p_visit_date::text || ':' || p_party_size::text,
      'sha256'
    ),
    'hex'
  );
$$;

-- 3. Bỏ RPC đọc khung giờ.
drop function if exists public.customer_list_product_slots(uuid, uuid, date);

-- 4. Thu khóa chính về ba cột. Chỉ chạy được khi truy vấn kiểm tra ở trên
--    không trả về hàng nào.
alter table public.customer_product_capacity_templates
  drop constraint if exists customer_product_capacity_templates_pkey;
alter table public.customer_product_capacity_templates
  add constraint customer_product_capacity_templates_pkey
  primary key (tenant_id, product_id, site_id);

-- 5. Thu `source_kind` về một giá trị. Chỉ chạy được khi chưa có hàng nào
--    dùng 'customer-approved' — kiểm bằng:
--      select count(*) from public.customer_product_capacity_templates
--      where source_kind <> 'catalog-staged';
alter table public.customer_product_capacity_templates
  drop constraint if exists customer_product_capacity_templates_source_kind_check;
alter table public.customer_product_capacity_templates
  add constraint customer_product_capacity_templates_source_kind_check
  check (source_kind = 'catalog-staged');

commit;
```

## Cách thử trước khi chạy thật

Đổi `commit;` cuối cùng thành `rollback;` rồi chạy:

```
npx supabase db query --linked --file <đường-dẫn>
```

Cách này chạy thật trên PostgreSQL production rồi vứt bỏ kết quả — bắt được đúng loại lỗi mà đọc SQL không thấy, và không để lại gì. Chính là cách `202608290050` được kiểm trước khi áp.

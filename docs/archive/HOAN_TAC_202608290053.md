# Đường hoàn tác cho `202608290053_customer_guest_groups.sql`

Production **không có PITR và không có bản sao lưu vật lý**, nên mọi migration chạm lược đồ đều phải có đường quay lại viết sẵn — viết lúc đang bình tĩnh, không phải lúc đang hỏng. Cùng lý do như [`HOAN_TAC_202608290050.md`](HOAN_TAC_202608290050.md).

## Migration này rủi ro tới đâu

Thấp hơn `202608290050` một bậc, và đây là ba lý do:

1. **Chỉ thêm cột và nới ràng buộc duy nhất.** Không xóa hàng nào, không đổi khóa chính, không đổi kiểu cột nào đang có.
2. **Chạy trọn trong một giao dịch.** Hỏng bất kỳ bước nào thì PostgreSQL tự cuộn lại toàn bộ.
3. **Đã chạy thử trên chính production** ngày 29/08/2026 bằng một giao dịch kết thúc bằng `rollback` — và không chỉ thử phần lược đồ: đã gọi thật cả hàm giữ chỗ lẫn hàm xác nhận, kiểm mười điểm, rồi vứt bỏ toàn bộ.

Chỗ thật sự cần cẩn thận là **hai hàm bị bỏ rồi tạo lại**. Bỏ hàm là mất luôn quyền đã cấp, nên phần `revoke`/`grant` ở cuối migration không phải trang trí — thiếu nó thì `service_role` gọi hàm sẽ bị từ chối.

## Ảnh chụp trước khi áp — 29/08/2026

Hai ràng buộc duy nhất sắp bị thay, đọc thẳng từ production:

| Bảng | Tên ràng buộc | Định nghĩa |
|---|---|---|
| `customer_order_lines` | `customer_order_lines_order_id_product_id_key` | `UNIQUE (order_id, product_id)` |
| `customer_order_tickets` | `customer_order_tickets_order_id_site_id_key` | `UNIQUE (order_id, site_id)` |

Tên đã kiểm bằng truy vấn thật, không đoán. Đoán sai tên thì `drop constraint if exists` **im lặng không làm gì**, ràng buộc cũ vẫn còn, và lỗi chỉ lộ ra lúc khách thật bấm đặt một đoàn có trẻ em.

## Điều kiện bắt buộc trước khi hoàn tác

Ràng buộc duy nhất cũ chỉ dựng lại được khi chưa có đơn nào tách hai nhóm. Kiểm trước, đừng đoán:

```sql
select order_id, product_id, count(*)
from public.customer_order_lines
group by 1, 2
having count(*) > 1;

select order_id, site_id, count(*)
from public.customer_order_tickets
group by 1, 2
having count(*) > 1;
```

Truy vấn nào trả về hàng thì **dừng lại**. Lúc đó đã có khách thật mua vé cho trẻ em; hoàn tác sẽ phải hủy những dòng đó, và đó là một quyết định kinh doanh của chủ dự án chứ không phải một câu lệnh.

## SQL hoàn tác

Chạy trọn trong một giao dịch. Đưa lược đồ về đúng trạng thái trước `202608290053`.

```sql
begin;

-- 1. Trả hàm xác nhận về bản phát một vé `group` cho mỗi chặng.
--    Thân hàm lấy nguyên văn từ `202608200043_customer_booking_on_erp_core.sql`
--    dòng 513–719. Chép lại từ đó, đừng viết lại từ đầu.
-- <dán nguyên văn hàm từ 202608200043 vào đây>

-- 2. Trả hàm giữ chỗ về chữ ký 8 tham số.
--    Thân hàm lấy nguyên văn từ `202608290051_customer_departure_waves.sql`
--    dòng 62–348.
drop function if exists public.customer_create_booking_hold(
  uuid, uuid, uuid, uuid, date, integer, timestamptz, timestamptz, integer, integer
);
-- <dán nguyên văn hàm 8 tham số từ 202608290051 vào đây>

revoke all on function public.customer_create_booking_hold(
  uuid, uuid, uuid, uuid, date, integer, timestamptz, timestamptz
) from public, anon, authenticated;
grant execute on function public.customer_create_booking_hold(
  uuid, uuid, uuid, uuid, date, integer, timestamptz, timestamptz
) to service_role;

-- 3. Trả dấu vân tay về 4 tham số.
drop function if exists public.customer_booking_payload_digest(
  uuid, date, integer, timestamptz, integer, integer
);
create or replace function public.customer_booking_payload_digest(
  p_product_id uuid,
  p_visit_date date,
  p_party_size integer,
  p_slot_starts_at timestamptz default null
)
returns text
language sql
immutable
security invoker
set search_path = ''
as $$
  select encode(
    extensions.digest(
      p_product_id::text || ':' || p_visit_date::text || ':' || p_party_size::text
        || ':' || coalesce(p_slot_starts_at::text, 'moi-khung'),
      'sha256'
    ),
    'hex'
  );
$$;
revoke all on function public.customer_booking_payload_digest(
  uuid, date, integer, timestamptz
) from public, anon, authenticated;
grant execute on function public.customer_booking_payload_digest(
  uuid, date, integer, timestamptz
) to service_role;

-- 4. Thu hai ràng buộc duy nhất. Chỉ chạy được khi hai truy vấn kiểm ở trên
--    không trả về hàng nào.
drop index if exists public.customer_order_lines_group_idx;
alter table public.customer_order_lines
  add constraint customer_order_lines_order_id_product_id_key
  unique (order_id, product_id);

drop index if exists public.customer_order_tickets_group_idx;
alter table public.customer_order_tickets
  add constraint customer_order_tickets_order_id_site_id_key
  unique (order_id, site_id);

-- 5. Trả ràng buộc tiền về cách tính cũ, rồi mới bỏ được cột.
--
--    Thứ tự bắt buộc: `customer_orders_total_check` tham chiếu `adults`, nên
--    bỏ cột trước là PostgreSQL từ chối.
--
--    ⚠ Chỉ chạy được khi **chưa có đơn nào có trẻ dưới 1m3**. Ràng buộc cũ là
--    `total_vnd = unit_price_vnd * party_size`; một đơn đã miễn phí cho em bé
--    có `total_vnd` nhỏ hơn thế và sẽ vi phạm ngay. Kiểm trước:
--      select count(*) from public.customer_orders where children > 0;
--    Khác 0 thì DỪNG — lúc đó hoàn tác nghĩa là tính lại tiền của khách thật,
--    và đó là quyết định của chủ dự án chứ không phải một câu lệnh.
alter table public.customer_orders
  drop constraint if exists customer_orders_total_check;
alter table public.customer_orders
  drop constraint if exists customer_orders_party_mix_check;
alter table public.customer_orders
  add constraint customer_orders_check
  check (total_vnd = unit_price_vnd * party_size);
alter table public.customer_orders
  drop column if exists adults,
  drop column if exists children;

alter table public.customer_order_lines
  drop constraint if exists customer_order_lines_guest_group_check;
alter table public.customer_order_lines drop column if exists guest_group;

alter table public.customer_order_tickets
  drop constraint if exists customer_order_tickets_guest_group_check;
alter table public.customer_order_tickets drop column if exists guest_group;

commit;
```

## Cách thử trước khi chạy thật

Đổi `commit;` cuối cùng thành `rollback;` rồi chạy:

```
npx supabase db query --linked --file <đường-dẫn>
```

Cách này chạy thật trên PostgreSQL production rồi vứt bỏ kết quả — bắt được đúng loại lỗi mà đọc SQL không thấy, và không để lại gì.

## Quy tắc giá đi kèm, đừng tách rời

Chủ dự án chốt 29/08/2026: **trẻ dưới 1m3 không mua vé**, từ 1m3 trở lên tính giá thường. Trong lược đồ, `child` vì thế có nghĩa hẹp là *khách dưới 1m3* — không phải "trẻ em" theo tuổi.

Hai thứ này phải đi cùng nhau, cả lúc áp lẫn lúc hoàn tác:

| Ràng buộc trên `customer_orders` | Dòng đơn `child` |
|---|---|
| `total_vnd = unit_price_vnd * adults` | đơn giá `0` |
| `total_vnd = unit_price_vnd * party_size` (bản cũ) | đơn giá `demo_price_vnd` |

Đổi một mà quên cái kia thì PostgreSQL chặn thẳng mọi đơn có trẻ nhỏ, và lỗi chỉ lộ ra lúc một gia đình thật bấm giữ chỗ.

## Một điều migration này **không** hoàn tác được

Vé đã phát ra rồi thì đã phát rồi. Sau khi áp, mỗi chặng phát hai tấm vé (`adult` và `child`) thay vì một tấm `group`. Hoàn tác lược đồ **không** gộp chúng lại — những tấm vé đó vẫn nằm trong `erp_tickets`, vẫn quét được ở cổng, và tổng số lượt vào vẫn đúng. Đó là hành vi mong muốn: không được hủy vé của khách đã trả tiền chỉ vì mình đổi ý về lược đồ.
